# Рабочее соглашение по проекту

Читай этот файл первым. Он про то, как здесь принято работать, а не про то, что делает проект — для этого есть `README.md` (обзор), `FIT-MODEL.md` (модель) и `help.html` (инструкция пользователя).

## Что за проект

Инструменты для самостоятельного bike-fit плюс раздел со статьями. Всё на ванильном JS с инлайновым SVG:

- `index.html` — сравнение геометрий двух рам,
- `fit-lab.html` — райдер на геометрии: кокпит, посадка сидя, атакующая стойка,
- `help.html` — справка по всем параметрам,
- `articles.html` — список статей, `article-<слаг>.html` — сами статьи.

## Как добавить статью

1. Создать `article-<слаг>.html` рядом с остальными страницами. Проще всего скопировать существующую статью и заменить содержимое: подключения (`site.css`, `read.css`, `nav.js`), оглавление слева, карточки с текстом, переключатель аналитики и тег GoatCounter в ней уже настроены. Собственного `<style>` у статьи почти нет и быть не должно — весь вид приходит из общих файлов.
2. Дописать одну запись **в начало** массива `POSTS` в `articles.html`:
   ```js
   { href:'article-<слаг>.html', date:'ГГГГ-ММ-ДД', tags:['исследование'],
     title:'…', lead:'…', read:'N минут' }
   ```
3. Порядок в массиве и есть порядок на странице — сортировки по дате нет намеренно, чтобы можно было закрепить важное наверху.

Грабли при переносе текста из markdown: если пункты нумерованного списка разделены пустой строкой, наивный конвертер закрывает `<ol>` на каждом и открывает новый — нумерация превращается в «1. 1. 1.». Проверять надо не глазами по коду, а счётом: у списка должен быть один `<ol>` на все пункты. Списки, разделённые абзацем текста, наоборот, обязаны остаться разными.

Навигацию рисует `nav.js` — массив `LINKS` внутри и есть весь список разделов, плюс отдельная ссылка `HOME` на сайт автора: она прижата вправо, отделена чертой и никогда не помечается текущим разделом, потому что ведёт наружу. Новая страница добавляется одной строкой там, и ссылка сразу появляется во всех шапках; в саму страницу вставляется `<script src="nav.js"></script>` на место шапки. Текущий раздел определяется по имени файла, `article-*.html` подсвечивает «Статьи», так что статьи в `LINKS` не заводятся.

## Жёсткие ограничения

- **Открывается двойным кликом с `file://`.** Без сборки, без npm-зависимостей, без сервера. Это и есть настоящее ограничение; «один файл на страницу» было лишь способом его соблюсти.
- **Общий код — только классическими `<script src>`.** ES-модули браузер с `file://` не грузит (CORS), `fetch` локальных файлов тоже запрещён. Обычный `<script src>` грузится. Поэтому `model.js` — это IIFE, кладущая себя в `window`, а не `export`.
- **Общая разметка вставляется синхронно**, через `document.currentScript.insertAdjacentHTML`, а не в `DOMContentLoaded`: иначе шапка появляется после отрисовки и сдвигает содержимое. Плата за вынос шапки — без JavaScript её не будет вовсе; для инструмента, который целиком на JavaScript, это ничего не меняет.
- Страница может подключать общие файлы (`site.css`, `tools.css`, `model.js`, `nav.js`), но не может зависеть от сети или от сборки. Инструменты разработки (`regress.mjs`) — отдельные файлы рядом, в страницу не входят.
- Никаких внешних CDN и сетевых запросов из страницы, кроме уже стоящей аналитики.

## Где чей стиль

Три уровня, и правило простое: **правится тот файл, где селектор уже живёт**.

- `site.css` — то, что одинаково везде: палитра `:root`, `body`, шапка, `.card`, каркас `.layout`/`.panel`.
- `tools.css` — виджеты страниц с расчётами. Отдельный файл, а не часть `site.css`, потому что здесь широкие селекторы по тегам (`button`, `svg`, `th`, `td`, `summary`); в справке и статьях те же теги оформлены иначе, и вливание изменило бы их вид.
- `read.css` — страницы, которые читают: справка и статьи. Раскладка «оглавление слева, текст справа», сама навигация по оглавлению, шапка материала и типографика текста. Здесь тоже широкие селекторы (`.card p`, `.card ul`, `h1`), поэтому он отдельно от `site.css` и никогда не подключается вместе с `tools.css`.
- `<style>` внутри страницы — только её собственные виджеты плюс короткие переопределения общего.

Две страницы с расчётами берут `site.css + tools.css`, справка и статьи — `site.css + read.css`. Список статей берёт только `site.css`: оглавления и текста статьи там нет.

Шапка материала — заголовок, мета-строка, лид — лежит **внутри первой карточки правой колонки**, а не над раскладкой. Иначе заголовок стоит выше оглавления, и они не выравниваются по верху.

Оба общих файла подключаются **перед** локальным `<style>`, поэтому страница всегда перебивает общее при равной специфичности. Перед выносом проверено, что ни одно вынесенное правило не полагалось на своё место в каскаде: пар «равная специфичность + общее свойство + один и тот же элемент» не нашлось.

## Регресс — обязателен при любой правке модели

```
node regress.mjs            сверить с эталоном
node regress.mjs --update   перезаписать эталон (только после разбора диффа)
node regress.mjs --list     выгрузить текущие значения
node regress.mjs --deploy   список файлов для хостинга и проверка ссылок
```

124 кейса, 4516 значений, допуск 1e-6. Покрыты **обе** страницы:

- **посадка** (`fit-lab.html`) — 72 кейса: две реальные связки рама+кокпит из `fixtures-evo.json` на сетке sag × наклон корпуса × разведение локтей × наклон велосипеда;
- **сравнение геометрий** (`index.html`) — 52 кейса: все геометрии фикстуры с заданной базой, каждая в четырёх состояниях — паспорт, sag 25%, ход +20, замена вилки.

Проверено, что сеть ловит поломку в каждой из страниц по отдельности.

Перед числами прогон делает **структурную проверку всех страниц**: подключены ли `site.css`, `read.css`, `nav.js` и `model.js`, не осталось ли ручной разметки шапки и задублированных стилей, ведут ли ссылки из `LINKS` на существующие файлы и подсвечивается ли ровно один раздел на каждой странице. Числа такую ошибку не ловят — расчёт от пропавшей шапки не меняется.

**Порядок действий:**

1. Перед правкой прогнать регресс — убедиться, что база чистая.
2. Внести изменение.
3. Прогнать снова, **разобрать каждое расхождение** и объяснить, почему оно ожидаемо. Расхождение, которое не удаётся объяснить, — это баг, а не повод обновить эталон.
4. Только после этого `--update` и запись в `CHANGELOG.md`.

Смысл зафиксированного `regress-golden.json` именно в том, чтобы ловить регрессии **между сессиями**. Снимок, снятый с текущего кода в начале работы, ловит только то, что сломалось в этом же разговоре; ошибка, заехавшая раньше, молча войдёт в новый снимок.

## Инварианты модели

Это свойства, которые обязаны выполняться. Каждое поймало реальный баг:

- **Солвер рамы один.** `model.js` — единственная реализация кинематики рамы; на страницах остались только тонкие обёртки, добавляющие своё (сдвиг на землю и `pitchSag` в Fit Lab, ETT/front center/виртуальная труба в сравнении). Физику правим в `model.js`; если правка понадобилась внутри обёртки — почти наверняка она не на своём месте.  
  Регресс продолжает гонять **обе** страницы, потому что обёртки тоже умеют ломаться.
- **Проверки вилки не влияют на расчёт.** `forkOffsetSpec` и `forkMeasLen` только сверяют введённую геометрию с железом. Если правка в них двигает хоть одно число в таблице — это баг.
- **RAD не зависит от sag.** Каретка и ручка жёстко на раме, расстояние между ними не может меняться от наклона. RAAD зависеть обязан.
- **При sag 0 и ходе, равном паспортному, таблица совпадает с паспортом** рамы до десятых.
- **Длина шатуна двигает высоту седла 1:1** в обратную сторону; толщина подошвы и платформа педали — 1:1 в ту же. Платформа лежит в `state.ck`, а не в `state.body`: читать её из мерок тела — тот самый баг, который однажды уже был.
- **Разведение локтей не меняет ни анатомический угол локтя, ни запас по длине руки, ни положение плеча.** Оно меняет только проекционный угол, вынос локтя вбок, отведение плеча и залом запястья.
- **Никаких NaN и Infinity** ни в одном выходе на всей сетке, включая вырожденные случаи (полный разгиб руки, недостижимый руль).

## Как устроено — тонкости реализации

Не очевидно из кода, ловилось болью:

**Пресеты.** Один ключ `bikelab.presets.v1` в `localStorage`, один JSON-блоб, три вида: `geo` (рама), `ck` (кокпит + шатун, Q-factor, штырь), `body` (мерки + наклон корпуса, целевое колено, множитель RAD). Имя пресета — ключ в объекте, поэтому сохранение под существующим именем обновляет запись.

Санация в два этапа. При **импорте** ключи приводятся к числу или `null`, но белый список НЕ применяется: иначе файл из более новой версии страницы навсегда терял бы незнакомые ключи. Белый список применяется при **загрузке в состояние**, поэтому мусор туда всё равно не попадёт. Плюс `fixReq()`: обязательные поля, пришедшие как `null`, откатываются к дефолтам — частичный пресет не должен ломать солвер.

`buildInputs()` сносит разметку карточек, поэтому обработчики делегированы на `document`, а выбранное в каждой строке хранится в `psSel` и восстанавливается вызовом `psRefresh()` в конце `buildInputs()`.

Пресет рамы, сохранённый без колёсной базы, при загрузке в Fit Lab получает её вычислением из офсета: здешний солвер без базы выдаёт `NaN`.

**Передача рамы между страницами.** Кнопка «Открыть в Fit Lab» собирает хэш `#w=<радиус>&n=<имя>&f=reach~stack~hta~sta~ht~st~cs~bbDrop~wb~travelRef~travel~sag`. Если база пустая, считается из офсета той же формулой, что в `solve()`. Проверено: после переноса reach, stack и углы совпадают до второго знака.

**Аналитика.** GoatCounter, один тег на страницу, без кук, адрес скрипта с явным `https`. Путь нормализован до имени файла — иначе `/папка/` и `/папка/index.html` считаются как две разные страницы. Локально с `file://` count.js не считает сам. Переключатель `#toggle-goatcounter` обрабатывается своим скриптом в `<head>`, а не штатным механизмом: страницы переписывают хеш своим состоянием раньше, чем догрузится асинхронный `count.js`. События шлются хелпером `track()` из обработчиков, а не атрибутами `data-goatcounter-click` — карточки пересобираются, атрибуты пришлось бы перепривязывать. Все вызовы обёрнуты в проверку `window.goatcounter`, блокировщик ничего не ломает.

**Раскладка.** Три точки: 700 и 1160 px, ширина левой панели `clamp(330px, 25%, 500px)`. Высота схем ограничена долей высоты окна с учётом пропорций viewBox — иначе вид сбоку при пропорции почти 1:1 не помещается рядом с полями.

## Стиль кода и текста

- Комментарии в коде объясняют **почему**, а не что. Особенно там, где выбрано неочевидное допущение — такие места должны говорить, какая альтернатива отвергнута и почему.
- Интерфейс и документация — по-русски, без англицизмов там, где есть нормальное слово. Термины, у которых нет русского эквивалента (reach, stack, RAD, sag, backsweep), оставляем как есть.
- Модель описательная, а не предписывающая: показывает числа, зоны и последствия, решение принимает человек. Автооптимизатора «идеальной посадки» здесь не будет — см. §3.5 роадмапа.
- Числа в ответах пользователю подкрепляй прогоном, а не памятью. Файлы между сессиями меняются: перечитывай код, прежде чем утверждать, как он работает.

## Чего не делать

- Не обновлять `regress-golden.json` «чтобы прошло».
- Не добавлять в модель параметры, которые нельзя ни измерить, ни откалибровать по фото: коэффициент, взятый с потолка, хуже честного отсутствия.
- Не заменять прямые замеры тела антропометрическими регрессиями — направление ровно обратное точности.
- Не ломать `file://`: ни `fetch` локальных файлов, ни модулей, ни сборки.
